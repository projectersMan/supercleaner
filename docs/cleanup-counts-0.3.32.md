# 清理计数、应用缓存与系统废纸篓进度 0.3.32（106）

## 已确认的原因

用户截图对应的实际记录包含 216 个扫描条目：8 个目录/文件成功移入废纸篓，208 个条目的状态为 `sourceMissing`。逐条核对路径后，这 208 项全部位于成功移走的父目录下。父目录先被移走，后代又作为独立目标执行，是本次数量差异及无效重复处理的原因。

## 修改

- 生成计划时，先对所有选中条目完成原有的风险、保护、扫描完整性和大文件保留对象检查，再合并已选父目录覆盖的后代。未选中的父目录不会自动加入计划；相似路径前缀及符号链接不构成目录覆盖。
- 勾选仍按原扫描条目保存，方便 Skill 整组选择和取消；底部摘要、生成的计划及执行进度采用同一组实际移动目标。应用卸载摘要与一键系统清理摘要也复用这一规则。
- Agent 扫描条目的大小是每个文件或目录的自身大小，因此合并操作时汇总其选中后代的容量。其他扫描器已经提供递归目录大小，合并后保留父目录的原容量，避免重复累计。
- 将废纸篓阶段的“已移入”计数改为“处理进度”，避免将失败或跳过的尝试描述为成功移动。弹窗和底部状态共用阶段文案。
- 等待单个系统废纸篓操作时，显示活动进度条以及每秒更新的当前文件耗时。完成数只在系统返回后增加；没有字节级进度时不制造百分比。
- 删除系统清理底部摘要中的 `Pending:`（中文的“待清理”前缀同步去掉）。
- 应用运行产生的缓存、派生日志及网页离线缓存进入 Recommended to Keep，默认不勾选，允许逐项选择。补充精确归属的 Application Support、沙盒及共享容器中的派生缓存路径；不将整个应用数据目录加入清理。
- 完整读取后容量确实为零的应用候选不再生成零容量行。权限不足、链接及不完整检查仍按原规则阻止执行，不能将它们当作空目录。
- 微信按实际 `xwechat_files/<account>/msg` 布局发现 `attach`、`file`、`video`、`migrate` 四类历史文件，不依赖版本字符串。它们属于个人文件，单独手动选择并要求微信退出；不包含账号根目录、消息数据库、凭据或整个 `msg` 目录。
